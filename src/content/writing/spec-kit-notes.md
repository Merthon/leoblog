刚接触 Spec Kit 时，我最想弄清楚的问题是：它到底是一个新工具，还是让 AI 写代码之前多聊几轮？

答案要从项目文件里找。Spec Kit 提供命令行工具、文档模板、脚本和编程助手集成。你仍然向 AI 描述需求，但讨论结果会逐步进入需求规格、技术方案和任务清单，后续实现也围绕这些文件推进。

下面以 Codex 和一个订单导出功能为例，说明它在日常开发中怎么使用。命令依据 2026 年 10 月 19 日的官方文档；不同版本、助手和集成模式的调用方式可能不同。

## Spec Kit 和 AI 编程助手各做什么

[Spec Kit](https://github.com/github/spec-kit) 是 GitHub 开源的开发流程工具包，核心支持规范驱动开发，也就是 Spec-Driven Development，简称 SDD。当前还提供可选的缺陷修复和想法评估流程，不必把所有工作都塞进一套功能开发步骤。

它不提供一个新的代码生成模型，也不是业务程序运行所需的框架。实际读取代码、修改文件和执行测试的，仍然是你使用的编程助手及其工具。

可以把职责分开看：

| 参与者 | 负责什么 |
| --- | --- |
| 开发者 | 提出目标、回答问题、确认取舍、审阅结果 |
| Spec Kit | 提供阶段指令、模板、辅助脚本和流程组织 |
| AI 编程助手 | 按指令读取项目、维护文档、实现代码和执行检查 |
| 测试与 CI | 检查可执行的规则，暴露真实失败 |

最后一行不能省。需求文件写着“权限隔离正确”，并不意味着导出接口真的不会越权。

## 安装与项目接入

下面采用官方支持的 PyPI 安装方式，需要 Python 3.11 及以上版本，并提前安装 `uv`。正式团队环境可以按[安装指南](https://github.github.io/spec-kit/installation.html)固定版本，避免不同开发者拿到不同模板。

这些命令在终端执行：

```bash
uv tool install specify-cli
specify version

# 创建新项目，明确选择 Codex 集成
specify init order-service --integration codex
cd order-service
```

CLI 的名字叫 `specify`。安装 CLI 和给某个项目接入流程是两件事；装好工具不代表所有仓库都已经配置完成。

如果代码已经存在，先提交或妥善保存当前修改，再建立用于接入的分支。在目标仓库根目录执行：

```bash
specify init --here --force --integration codex
git diff
git status --short
```

这里的 `--force` 可能覆盖冲突的工具管理文件，不该不看提示就执行。除了 `git diff`，还要检查未跟踪的新文件。初始化不会重写整个业务系统，也不会自动补齐旧代码的需求说明。[已有项目指南](https://github.github.io/spec-kit/guides/existing-projects.html)建议从一个边界清楚的改动开始。

以上只是用法示例，不需要把 Spec Kit 本身的源码仓库复制进业务项目。

## 在 Codex 中如何操作

Spec Kit 的 [Codex 集成](https://github.github.io/spec-kit/reference/integrations.html)把 Skills 放到项目的 `.agents/skills/`，使用 `$speckit-<阶段>` 调用。Copilot 默认使用的 `/speckit-<阶段>`，以及部分文档里的点号写法，不应该不加区分地照搬。

接入后，在目标项目中打开 Codex，确认相关 Skills 已被发现，再把下面的内容发送到对话框。**这些是给编程助手的指令，不是 Shell 命令。**

项目开始时，先建立共同规则：

```text
$speckit-constitution
遵循现有分层和代码风格，不随意新增依赖。
涉及权限的功能必须有允许访问和拒绝访问的测试。
新增功能保持现有 API 兼容；执行项目已有的检查命令。
```

规则只写团队确实愿意执行的内容。没有必要为了填满模板，临时宣布整个项目改成微服务或全面采用 TDD。

接着描述一个功能：

```text
$speckit-specify
为订单管理增加 CSV 导出。
只能导出当前用户有权限查看的订单，支持日期和状态筛选。
本期不做定时导出。先整理需求，不实现代码。
```

不要在这一刻急着决定用哪个 CSV 库。先明确导出的行为：是当前页还是全部筛选结果？字段有哪些？超过数量限制时怎么办？

存在这些疑问时，可以调用：

```text
$speckit-clarify
重点确认导出范围、数量上限、字段以及失败时的表现。
```

需求确认后再规划实现。例如，假设项目本来就是 Java 技术栈：

```text
$speckit-plan
沿用现有 Spring Boot 和 PostgreSQL。
复用已有鉴权与订单查询逻辑，不新增独立服务。
评估大结果集的内存占用和 CSV 公式注入风险，并说明处理方式。
```

这些描述只是示例，不是 Spec Kit 对语言或架构的要求。它不会因为某个项目用了 Java，就要求其他项目也这样写。

## 从文档进入代码

规划完成后，再逐个运行以下阶段，每一步都看过结果后继续：

| Codex 指令 | 要关注的结果 |
| --- | --- |
| `$speckit-tasks` | 任务顺序是否合理，是否包含必要测试 |
| `$speckit-analyze` | 需求、方案和任务有没有冲突或遗漏 |
| `$speckit-implement` | 代码变更与实际检查结果 |
| `$speckit-converge` | 实现对照文档还缺哪些工作 |

按当前[命令参考](https://github.github.io/spec-kit/reference/agentic-sdd.html)，`analyze` 做只读一致性分析；`converge` 不直接修代码，发现缺口时向任务清单追加工作，再由 `implement` 继续处理。需求质量检查清单也不等于测试通过记录。

对于稍大的功能，我更倾向于限制一次执行的范围：

```text
$speckit-implement
只实现导出接口及权限测试，不修改前端。
完成后汇报修改文件、执行过的测试和未验证项，先停下来。
```

这样审阅时可以集中检查：查询有没有复用权限条件？测试有没有覆盖跨用户访问？生成 CSV 的过程是否一次性把所有订单放进内存？这些问题比一份勾满的任务清单更能说明实现质量。

## 项目里会留下什么

以 Codex 集成为例，执行相关阶段后，目录大致如下。功能目录名称仅作示意，不要求采用这个命名：

```text
order-service/
├── .agents/skills/            # Codex 使用的阶段指令
├── .specify/                 # 项目规则、模板、脚本和流程状态
├── specs/
│   └── order-export/
│       ├── spec.md           # 要做什么、边界在哪里
│       ├── plan.md           # 技术实现方案
│       └── tasks.md          # 具体任务与进度
├── src/                      # 实际业务代码
└── tests/                    # 示例测试目录
```

实际项目还可能产生研究、数据模型或接口约定等材料。文件按阶段逐步生成，不是安装后就有了完整规格。

[官方快速入门](https://github.github.io/spec-kit/quickstart.html)还说明，当前功能由 `.specify/feature.json` 等机制定位，不能只靠切换 Git 分支就假定流程也切换到了另一个功能。跨功能工作时，要确认助手正在处理哪个目录。

这些 Markdown 可以直接在编辑器里改，也可以明确要求 AI 修改。使用 Spec Kit 不等于每个字都必须通过聊天输入。

## 仍然通过对话 但不能只依赖聊天

如果使用的是能访问项目的 Codex，调用 Skill 后，助手会读取对应指令，再按需要读写文件或运行脚本。[OpenAI 的 Skills 文档](https://learn.chatgpt.com/docs/build-skills)支持显式调用，也支持按任务匹配；需要明确执行某一阶段时，我更愿意点名对应 Skill。

普通聊天环境如果没有项目访问能力，只能协助起草和讨论，不能因为发了同样的指令就直接修改本地仓库。安装 Spec Kit 也不会自动让所有后续聊天进入它的流程。

日常维护时，真正要注意的是文档与代码是否同步。例如，导出上限由一万条改成五万条，不能只让 AI 修改一个常量。限制变化可能影响接口行为、内存策略和测试数据，应检查相关文件是否也需要调整。

[规格维护指南](https://github.github.io/spec-kit/guides/evolving-specs.html)提供了保留历史规格、持续维护同一份规格，以及让实现发现反馈到规格等方式。团队需要选定自己的约定，避免有人把旧文档当历史记录，有人却把它当当前行为。

我会把相关文档和代码一起放进审阅范围。新会话接手时，也要明确功能目录、当前任务和不能修改的部分，而不是期待 AI 记住上一次全部讨论。

## 什么时候值得使用

我的判断是，涉及权限、多个模块、复杂验收条件，或者需要长期交接的功能，更适合使用这套流程。单行修复、改文案、一次性实验，不必为了完整跑流程而制造文档。

它不会让错误需求自动变正确，也不会让 AI 的自检变成可信的安全审计。隐私数据、密钥和真实客户信息仍然不应该写进规格；第三方扩展和脚本也要先审查再运行。

如果准备试用，我会选一个能独立验收的小功能，观察两件事：前期审阅有没有减少后期返工，留下的文档在下一次修改时是否真的有用。两者都没有改善，就该缩短流程，而不是继续增加模板。
