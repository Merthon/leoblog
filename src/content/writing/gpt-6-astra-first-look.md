模型发布时，人们习惯先找跑分、上下文长度和价格。GPT-6 Astra 当然也有这些数字，但我更在意另一件事：它开始认真处理真实工作里那些“不整齐”的部分。

工具不会同时返回，需求可能在执行途中改变，同一个任务的不同阶段也不需要相同的推理强度。以前，这些问题主要由智能体框架在模型外面处理；Astra 把其中一部分纳入了模型与 API 的协作方式。

## 从回答问题到推进流程

OpenAI 将 GPT-6 Astra 定位为面向复杂端到端工作的模型，覆盖编程、浏览器操作、研究和文档制作。它支持 105 万 token 的上下文窗口，单次最多输出 12.8 万 token，并可以通过 Responses API 使用网页搜索、文件搜索、代码解释器、托管 Shell、计算机操作、MCP 和 Skills 等工具。[查看模型说明](https://developers.openai.com/api/docs/models/gpt-6-astra)

这些能力放在一起，意味着模型面对的不再只是一段输入。它要阅读环境、调用工具、观察结果，再继续做决定。对程序员来说，这更接近一个会操作工作区的执行者。

真正有意思的是异步工具调用。应用可以把某个工具标记为异步，让 Astra 在工具运行期间继续思考、处理其他部分，等结果准备好后再通过原来的 `call_id` 交回来。一次缓慢的查询，不必让整条任务链停在那里等待。

这很像我们熟悉的并发程序：等待 I/O 时，进程还能推进别的工作。区别在于，调度对象从固定代码变成了带有判断能力的模型。应用仍然负责真正执行工具和管理未完成任务，模型并没有凭空获得系统权限。

## 任务进行中，也可以改方向

Astra 还支持中途调整。通过 WebSocket，用户可以在模型工作时补充要求、纠正方向，或者改变目标。已经完成的部分会被保留，新要求进入当前任务的后续流程。[查看 GPT-6 Astra 使用指南](https://developers.openai.com/api/docs/guides/latest-model)

这个能力听起来普通，实际很重要。长任务很少能靠第一次描述就完全说清楚。过去我们只能等待整轮结束，再带着新提示重新开始；现在更像和同事一起工作，看到方向不对时可以及时说一句：“这一部分先停，优先处理刚发现的问题。”

推理强度也能在对话中调整。例行整理可以使用较低强度，遇到架构取舍或疑难故障时再提高，而不需要重写前面的提示词。Astra 支持 `low`、`medium`、`high`、`xhigh` 和 `max`，但不支持完全关闭推理的 `none`。

## 百万上下文不是免费硬盘

105 万 token 很宽裕，却不代表应该把整个知识库直接塞进去。官方定价中，文本输入为每百万 token 10 美元，缓存输入为 1 美元，输出为 50 美元；当输入超过 27.2 万 token 后，整次请求会进入更高费率。[查看模型价格与限制](https://developers.openai.com/api/docs/models/gpt-6-astra)

这会逼着应用认真管理上下文。稳定的系统说明适合缓存，历史过程需要压缩，外部资料应该按任务检索。上下文越长，模型要分辨的噪声也越多。容量解决了“放不下”，没有解决“该放什么”。

我也不会把 Astra 用在每一个请求上。格式转换、简单分类和高频接口更适合便宜的小模型。Astra 的价值应该按任务完成成本衡量：它能否少走几轮、少返工一次，或者独立完成原本需要多个工具拼接的工作。

## 能力越完整，边界越要清楚

当模型可以操作文件、浏览网页和运行命令，提示词就不再只是写作要求，它还是权限边界的一部分。哪些目录能改、什么操作必须询问、失败后如何回滚，都应该由应用明确规定，并由代码真正限制。

OpenAI 的指南提到，Astra 更擅长遵守任务边界，也更容易受到 `AGENTS.md`、Skills 等环境指令的影响。对开发者来说，这既是能力，也是需要审计的输入面。项目里一份过时的说明，可能比一句临时提示更持续地影响任务方向。

我对 Astra 最直接的感受，是模型能力和工程控制正在靠得更近。下一步不只是写出更长的提示词，而是把任务拆分、权限、缓存、工具状态和验收标准设计成一套可以持续运行的系统。模型负责推进工作，系统负责让这份推进可见、可停，也能撤销。
